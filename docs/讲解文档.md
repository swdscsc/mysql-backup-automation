# mysql-backup-automation 讲解文档

## 一、先理解一句话

> **备份不是目的，能恢复才是目的。**

这句行业共识是所有设计的出发点。面试时聊备份话题，先把这句说出来，
后面所有的设计（为什么要校验、为什么要演练）就都顺理成章了。

一个真实的事故模型：磁盘上躺着 30 天的备份，某天数据库崩了，
恢复时发现最近 7 天的备份全是坏的（因为磁盘早就满了，mysqldump 静默失败）。
**有备份 ≠ 能恢复**。这个项目就是防止这种事。

## 二、代码走读

### backup.sh

```bash
mysqldump $MY_OPTS \
    --single-transaction \
    --routines --triggers --events \
    --default-character-set=utf8mb4 \
    "$DB" | gzip -9 > "$FILE"
```

四个参数每个都有讲究，面试常问：

| 参数 | 不加会怎样 |
| --- | --- |
| `--single-transaction` | 要么锁表（业务中断），要么备份数据不一致（订单表和库存表对不上） |
| `--routines` | 存储过程丢失，恢复后业务报错「procedure not found」 |
| `--triggers` | 触发器丢失，数据一致性靠触发器的逻辑全废 |
| `--events` | 定时事件丢失，定时任务不执行 |

**`| gzip -9 > file` 管道直接压缩**：不先落盘 .sql 再压，省一次磁盘 IO，
大库备份时这个差别很明显（100GB 的库能省一半时间和一半临时空间）。

**清理过期备份**：
```bash
find "$BACKUP_DIR" -maxdepth 1 -type d -mtime +"$RETENTION_DAYS" -exec rm -rf {} +
```
`-maxdepth 1` 是关键——限制只删一级目录，防止 `find` 递归下去误删。
这种破坏性命令必须加范围限制。

### verify_backup.py

```python
def md5_of_file(path, chunk=1 << 20):
    h = hashlib.md5()
    with open(path, "rb") as f:
        while True:
            b = f.read(chunk)
            if not b: break
            h.update(b)
    return h.hexdigest()
```

**为什么分块读（1MB）而不是 `f.read()` 一次性读？**
数据库备份动辄几十 GB，一次性读进内存会直接 OOM。分块读内存占用恒定在 1MB。
这跟日志分析工具里用生成器是同一个道理：**处理大文件时，永远不要让内存占用随文件大小增长**。

**最关键的一项检查**：
```python
DUMPED_RE = re.compile(rb"-- Dump completed")
check("转储完整结束", bool(DUMPED_RE.search(content)), ...)
```

为什么这一项最重要？看实测结果——那个坏备份：

- MD5 ✓（文件确实没被改动过）
- gzip 能解压 ✓
- 有 CREATE TABLE ✓
- 有 INSERT ✓

**五项全过，但它是坏的。** 因为它是备份过程中被截断的，最后一张表的数据根本没写进去。
只靠 MD5 和解压检查发现不了，必须看结束标记。

这个例子面试时讲出来非常有说服力——它证明你理解「校验什么」比「校验了」更重要。

### restore.sh

三重防护，每重对应一个真实事故场景：

| 防护 | 防的事故 |
| --- | --- |
| 恢复前先跑 `verify_backup.py`，不过就拒绝 | 用坏备份覆盖了仅有的好数据 |
| 恢复前先把目标库导出一份 | 恢复错了没退路 |
| 默认演练 + 非空库二次确认 | 手滑把生产库覆盖了 |

**`trap cleanup EXIT`** 保证临时密码文件一定会被删除（哪怕脚本中途出错退出），
避免密码文件残留在 `/tmp` 里。

## 三、面试问答

**Q：mysqldump 备份期间业务能正常写入吗？**
> InnoDB + `--single-transaction` 可以。它在事务里拿一致性快照（依赖 MVCC），不锁表。
> 但如果表是 MyISAM 就必须锁表；另外备份期间如果有 DDL（ALTER TABLE），
> 会导致快照不一致甚至备份失败，所以备份窗口要避开变更发布。

**Q：备份文件要保留多久？**
> 看业务和合规要求。我脚本默认 7 天，实际生产通常是：
> 日备保留 7~30 天，周备保留 3 个月，月备保留 1 年。
> 还要考虑**异地**：本地备份和数据库在同一个机房，机房出事就全没了，
> 所以至少要有一份在对象存储（S3/COS/OSS）上。

**Q：怎么验证备份真的能恢复？**
> 两个层次：
> ① 静态校验（本项目做的）：检查文件完整性、结束标记、表数量；
> ② 真实演练：定期（比如每月）自动恢复到一台临时实例，跑一遍核心查询比对行数。
> 只有第二层才算真正验证过。第一层是低成本的日常检查，第二层是定期的深度验证。

**Q：数据量很大（比如 500GB）时，mysqldump 还合适吗？**
> 不合适。mysqldump 是逻辑备份，500GB 导出+恢复要几小时，业务等不起。
> 大库应该用**物理备份**：Percona XtraBackup，直接拷贝数据文件，
> 支持增量备份，恢复速度快一个数量级。
> mysqldump 适合中小库（几十 GB 以内）和需要跨版本迁移的场景。

**Q：如果要求恢复到「昨天下午 3 点」这个精确时刻，怎么做？**
> 全量备份 + binlog 做**时间点恢复（PITR）**：
> 先恢复最近一次全量备份，再重放 binlog 到指定时间点。
> 前提是 binlog 一直开着（`log_bin=1`）且保留足够久。
> 这也是为什么生产环境必须开 binlog——它同时还是主从复制的基础。

**Q：这个项目还有什么不足？**
> ① 没有异地备份，本机磁盘故障就一起没了；
> ② 只做全量，没做 binlog 增量，无法精确到时间点恢复；
> ③ 恢复演练还得人工触发，没做成定期自动任务。
> 这三点我都写在 README 的后续计划里了。
